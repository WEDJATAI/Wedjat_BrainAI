# 2. THE MOST IMPORTANT PRINCIPLE

The Brain is the complete system around the model.

The model is responsible for tasks such as:

* language generation
* reasoning
* interpretation
* planning
* classification
* extraction
* tool selection
* multimodal interpretation

The Brain is responsible for:

* identity
* authorization
* memory
* knowledge
* evidence
* retrieval
* provenance
* context construction
* policy
* tool governance
* model selection
* verification
* state
* learning
* evaluation
* feedback
* auditing
* reliability
* cost control

The model must never be the final authority for authorization, truth, system policy, tenant access, or external side effects.

# 4. WEDJAT BRAIN CONSTITUTION

The following rules are mandatory and override convenience.

## Rule 1 — No false intelligence claims

Do not claim that Wedjat trained its underlying model when the system merely:

* stored memory
* added documents
* updated prompts
* changed retrieval
* changed routing
* changed tool policies

Use accurate terminology.

---

## Rule 2 — Model output is not automatically truth

Never automatically convert:

```text
LLM output
```

into:

```text
verified knowledge
```

unless independent evidence or an explicit validated workflow justifies doing so.

---

## Rule 3 — Authorization is outside the model

The model may request an action.

The policy/authorization layer decides whether that action is permitted.

---

## Rule 4 — Retrieved content is untrusted

Documents, websites, emails, tool results, user-provided text, and external data may contain malicious instructions.

They must never be treated as system-level instructions.

---

## Rule 5 — Tenant isolation is mandatory

The Brain must never leak:

* memories
* documents
* knowledge
* conversation information
* tools
* data
* credentials
* hidden metadata

between unauthorized tenants, users, applications, or organizations.

---

## Rule 6 — Side effects require explicit authorization

A model recommendation is not execution.

Distinguish:

```text
recommendation
draft
simulation
requested action
authorized action
executed action
verified result
```

---

## Rule 7 — Important knowledge has provenance

The Brain must be able to determine:

```text
where did this information come from?
when was it obtained?
what evidence supports it?
what version was used?
is it still valid?
does conflicting evidence exist?
```

---

## Rule 8 — Knowledge is temporal

The Brain must distinguish:

```text
current
historical
future/scheduled
expired
unknown
conflicted
```

---

## Rule 9 — Learning is controlled

Production activity may generate:

```text
learning candidates
```

It must not silently modify trusted knowledge, prompts, policies, or model behavior.

---

## Rule 10 — Simplicity wins unless complexity is justified

Do not introduce:

* another database
* another vector database
* another queue
* another gateway
* another microservice
* another cache
* another orchestration system

without a measurable reason.

---

## Rule 11 — Logical modularity does not require microservices

Implement strong boundaries in code first.

Create physically independent services only when justified by:

* scale
* security
* deployment independence
* reliability
* performance
* organizational ownership

---

## Rule 12 — Every capability must be testable

Nothing is “done” because code exists.

A capability is done only when:

```text
implemented
+
tested
+
secured
+
observable
+
documented
+
deployed
+
verified
```

* document ingestion

Use one primary model-access abstraction.

Do not hard-code every product to one vendor API.

## Turso

Use only where actual requirements justify it:

* local inference
* embedded data
* offline operation
* mobile/device-local retrieval
* edge caching
* regional/local vector access

Do not maintain duplicate canonical memory simply because Turso supports vectors.

# 20. MEMORY ARCHITECTURE

Implement three explicit memory domains.

## 20.1 EPISODIC MEMORY

Records what happened.

Examples:

```text
conversation
message
action
tool call
observation
event
outcome
decision
```

Do not replace raw historical records with summaries.

Summaries are derived representations.

---

## 20.2 SEMANTIC MEMORY

Stores useful durable information.

Examples:

```text
user preference
organization fact
recurring requirement
known system relationship
durable project fact
```

Every durable semantic memory should support:

```text
memoryId
tenantId
scope
type
content
source
confidence/evidence state
createdAt
updatedAt
validFrom
validUntil
status
version
supersedes
supersededBy
```

---

## 20.3 PROCEDURAL MEMORY

Stores how something should be done.

Examples:

```text
workflow
procedure
playbook
tool procedure
domain operating sequence
```

Procedural memory must be versioned.

Do not let a casual conversational message silently replace a trusted operational procedure.

# 23. MEMORY PROMOTION RULES

Strong promotion signals may include:

* explicit user instruction to remember
* confirmed stable preference
* repeatedly observed stable fact
* verified external fact
* confirmed workflow state

Weak signals include:

* one-off model assumptions
* speculative conclusions
* inferred personality claims
* unverified statements
* temporary conversation context

Do not confuse repetition with truth.

---

# 24. MEMORY DECAY

Memory relevance can decay.

Do not delete required history merely because relevance declines.

Maintain separate concepts:

```text
historical retention
```

and:

```text
retrieval relevance
```

A five-year-old event can remain historically important while receiving low default retrieval weight.

---

# 25. MEMORY CONSOLIDATION

Use scheduled workflows to:

```text

 ↓
promote stable memories
 ↓
preserve historical events
```

Do not repeatedly feed the entire historical database into the model.

# 35. SEMANTIC RETRIEVAL

Use embeddings for:

* semantic similarity
* conceptual recall
* related memories
* related documents
* approximate meaning

Do not expect vectors to solve:

* exact IDs
* exact codes
* numbers
* legal citations
* dates
* version identifiers

---

# 36. KEYWORD RETRIEVAL

Use lexical search when the task requires:

* exact terms
* names
* identifiers
* product codes
* legal clauses

# 37. STRUCTURED RETRIEVAL


* equate RAG with intelligence
* equate embeddings with learning
